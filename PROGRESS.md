# P2. Авторизация через Telegram

Ветка: `feat/telegram-auth`
Статус: план составлен, ждёт согласования. Кода ещё нет.

P1 закрыта и влита в `main` — см. `docs/progress/P1-async-generation-owner-id.md`.

---

## Цель

Пользователь, пришедший из Telegram, получает рабочий аккаунт — без регистрации,
логина и пароля. Дальше он для системы неотличим от обычного веб-пользователя:
та же сессионная кука, тот же owner-скоупинг, те же эндпоинты.

## Что уже есть и менять не нужно

Проверено по коду:

- `SessionAuthMiddleware` резолвит принципала по куке `presenton_session` —
  откуда взялась кука, ей безразлично;
- изоляция данных обеспечена глобальным owner-скоупингом в
  `services/database.py`, а не проверками в роутах;
- `User.username` — уникальный индексированный `String(128)`, значение
  `tg_<id>` в него ложится → **миграция не нужна**;
- регрессионный тест из P1 подтверждает, что асинхронная генерация проставляет
  владельца.

Колонку `telegram_id` не добавляем: обратный поиск пока не нужен, уникальности
`username` достаточно. Понадобится — это одна миграция, сделаем тогда.

## Целевой флоу

```
Mini App                        Наш backend
--------                        -----------
Telegram.WebApp.initData
   |
   | POST /api/v1/auth/telegram
   |    { "init_data": "<raw query string>" }
   v
                                1. проверить HMAC-подпись
                                2. проверить свежесть auth_date
                                3. найти или создать User(username=f"tg_{id}")
                                4. get_jwt_strategy().write_token(user)
                                5. _set_login_cookie(...)
   |
   |<-- 200 + Set-Cookie: presenton_session=...
   v
дальше обычные запросы с кукой
```

### Проверка подписи

Алгоритм Telegram, без новых зависимостей — `hmac` и `hashlib` из stdlib:

1. распарсить `init_data` как query string;
2. изъять параметр `hash`;
3. остальные пары отсортировать по ключу, склеить как `key=value` через `\n`
   (data_check_string);
4. `secret_key = HMAC_SHA256(key=b"WebAppData", msg=bot_token)`;
5. сравнить `HMAC_SHA256(key=secret_key, msg=data_check_string)` с `hash` через
   `hmac.compare_digest`.

Токен бота — новая переменная `TELEGRAM_BOT_TOKEN`, аксессор в
`utils/get_env.py` по существующему шаблону (`get_telegram_bot_token_env`).

Если токен не задан, эндпоинт отвечает **503**, а не 500: это ошибка
конфигурации развёртывания, и её надо отличать от сбоя в коде.

### Свежесть auth_date

`initData` живёт в WebView долго, поэтому подпись сама по себе не защищает от
повторного использования старого значения. Отвергаем `auth_date` старше
**15 минут**.

Почему 15: Telegram рекомендует до 24 часов для некритичных случаев и короче для
остальных. Здесь выдаётся сессия на 30 дней (`SESSION_TTL_SECONDS`), так что
окно короткое. Не 5 — чтобы не ловить отказы на расхождении часов сервера.

## Открытые решения

Каждый пункт меняет реализацию, поэтому до кода.

### 1. Сколько ботов поддерживаем

Предполагается один `TELEGRAM_BOT_TOKEN`. Если ботов будет два (тестовый и
боевой), подпись от второго не пройдёт.

Предлагаю **одну переменную**; для тестового бота — отдельное развёртывание.
Список токенов — усложнение под сценарий, которого пока нет.

### 2. Rate limiting

`POST /login` защищён на двух уровнях: nginx (`limit_req zone=auth_login`,
10 запросов в минуту на IP) и `LoginRateLimiter` в приложении (5 неудач за
5 минут на пару IP+username).

Для `/auth/telegram` перебор невозможен — HMAC не подделать. Но эндпоинт
публичный и **создаёт пользователей**, то есть это точка роста БД.

Предлагаю добавить в `nginx.conf` по образцу `/api/v1/auth/login`, отдельную
`limit_req_zone`. `LoginRateLimiter` не подключать: он про неудачные пароли,
здесь их нет.

### 3. Что возвращать в теле ответа

`/login` возвращает `{configured, authenticated, **serialize_user(user)}`.

Предлагаю то же плюс `"created": true/false` — Mini App сможет показать
приветствие новому пользователю. Одно поле, польза сразу.

### 4. Имя пользователя

`tg_<telegram_user_id>`, только цифровой id. Не `@username` из Telegram: тот
меняется, а id — нет.

Побочный эффект: в веб-интерфейсе такой пользователь виден как `tg_123456789`.
Для v1 нормально; человеческое имя — отдельное поле и отдельная задача.

Заметка на будущее: логин сравнивает имена регистронезависимо
(`func.lower(User.username) == username.casefold()`). У `tg_<цифры>` регистра
нет, коллизий не будет. Но надо проверить, что обычный пользователь не может
занять себе имя `tg_123` — иначе это способ перехватить чужой TG-аккаунт. Сейчас
пользователей создаёт только админ (`POST /api/v1/admin/users`), так что риск
теоретический, но в P6 (политика регистрации) про это помнить обязательно.

### 5. Пароль для TG-аккаунтов

Модель требует `hashed_password`. Ставим хеш от случайной строки
(`secrets.token_urlsafe(32)`), сам пароль не сохраняем — войти по нему нельзя,
только через Telegram.

Альтернатива — сделать колонку nullable: миграция плюс новая ветка «а если
пароля нет» во всех проверках. Не стоит того.

## План работ

### Шаг 1. Верификация initData

Новый модуль `api/v1/auth/telegram.py`: чистая функция
`parse_and_verify_init_data(init_data, bot_token, max_age_seconds) -> dict`.
Без FastAPI и без БД — только разбор и проверка подписи.

Юнит-тесты в `tests/unit/`:

- корректная подпись проходит;
- испорченная подпись отвергается;
- отсутствующий `hash` отвергается;
- просроченный `auth_date` отвергается;
- подпись другим токеном бота отвергается.

Тестовые данные генерируются в тесте тем же алгоритмом — фикстуры с настоящими
`initData` не нужны.

### Шаг 2. Эндпоинт

`POST /api/v1/auth/telegram` в `api/v1/auth/router.py`:

- схема `TelegramAuthRequest` в `api/v1/auth/schemas.py` (одно поле `init_data`);
- get-or-create пользователя;
- кука через существующий `_set_login_cookie`.

Путь добавить в `SessionAuthMiddleware._PUBLIC_AUTH_PATHS` — иначе middleware
потребует авторизацию у эндпоинта, который её выдаёт.

Гонка при одновременном первом входе: два параллельных запроса могут оба не
найти пользователя и оба попытаться создать. Ловим `IntegrityError` и
перечитываем — как в `POST /setup` и `POST /admin/users`.

### Шаг 3. Интеграционный тест

По образцу `tests/integration/test_auth_endpoints.py`:

- первый вход создаёт пользователя и возвращает куку;
- второй вход тем же `initData` переиспользует того же пользователя, не плодит
  дубли;
- полученной кукой можно дойти до защищённого эндпоинта;
- невалидный `initData` → 401, куки нет;
- `TELEGRAM_BOT_TOKEN` не задан → 503.

### Шаг 4. Конфигурация и документация

- `TELEGRAM_BOT_TOKEN` в `docker-compose.yml` (оба сервиса) и в `README.md`;
- `limit_req_zone` в `nginx.conf` (если по п.2 решение «да»);
- обновить `tg.md`: точный контракт эндпоинта для разработчика бота.

### Шаг 5. Проверка

- `.venv/bin/python -m pytest tests/unit tests/integration -q` — сейчас
  700 проходит, должно остаться зелёным;
- живой запуск: сгенерировать `initData` локально валидным тестовым токеном,
  дойти до создания презентации.

## Чего в этой задаче НЕ делаем

- **Куку для iframe** (`SameSite=None; Secure`) — это P5, зависит от HTTPS.
  В мобильном Telegram WebView текущий `SameSite=Lax` работает, на
  `web.telegram.org` — нет. Здесь не трогаем, чтобы не смешивать причины отказов.
- **Аутентификацию бота** (не Mini App). Бот — серверный процесс, `initData` у
  него нет. Как он получает сессию пользователя — открытый вопрос к разработчику
  бота, зафиксирован в `tg.md`.
- **Квоты** — P4.
- **Политику регистрации** — P6.

## Вопросы

1. **Rate limiting на `/auth/telegram`** — добавляем в nginx сразу или потом?
2. **`TELEGRAM_BOT_TOKEN`** — есть ли у тебя токен тестового бота? Для шага 5
   годится любой валидный по форме: проверка подписи к Telegram API не
   обращается, так что даже отозванный подойдёт. Если нет — сгенерирую тестовое
   значение сам, но тогда живую проверку с настоящим Mini App делать не на чем.
3. **`"created": true/false` в ответе** — нужно или лишнее?
